UC10: Produktinstanzen mit MHD

Use-Case 10 | Status: ⏳ TODO (PRIORITÄT!)

📋 Übersicht

Beschreibung: ZENTRALE UC! Verwaltung von konkreten gekauften Produktinstanzen mit individuellem MHD. Dies ist das Kernmodell der gesamten Anwendung.

Hauptziele

  • ProduktInstanz-Records mit eigenem MHD verwalten
  • CRUD für ProduktInstanzen
  • Jedes gekaufte Produkt = EINE ProduktInstanz (nicht ein MHD pro Lebensmittel!)
  • Lagerort, Menge, MHD tracken

Geschäftsnutzen & Design-Decision

⭐ Zentral: Eine "Portion Joghurt" = 1 ProduktInstanz mit eigenem MHD, nicht ein globales "Joghurt" MHD. Dies ermöglicht flexibles Tracking von Mehrfach-Käufen mit unterschiedlichen Verfallsdaten.

📦 Domain Model

Beteiligte Entities

Entity Rolle Beziehung
ProduktInstanz Zu verwaltende Einheit (ZENTRAL!) Primary (CRUD-Ziel)
LebensmittelKatalog Referenz-Template Foreign Key (1..1)
Lagerort Speicherort Foreign Key (0..1)

ProduktInstanz Entity

ProduktInstanz
├── Id: int (PK)
├── LebensmittelKatalogId: int (FK) ← WELCHES Produkt?
├── Menge: decimal ← WIE VIEL?
├── Einheit: string (g, ml, Stück, etc.)
├── MHD: DateTime ← WANN VERFÄLLT DIESES?
├── LagerortId: int? (FK, nullable) ← WO LAGERT ES?
├── Barcode: string (optional)
├── KaufDatum: DateTime
└── Notiz: string (optional)

BEACHTE: Kein globales "MHD pro LebensmittelKatalog"
         Jede INSTANZ hat ihr eigenes MHD!

Daten-Beispiel

LebensmittelKatalog: Joghurt (generisch)
├── ProduktInstanz #1: 500g, MHD 2026-06-20, Kühlschrank
├── ProduktInstanz #2: 500g, MHD 2026-06-25, Kühlschrank (2. gekauft)
└── ProduktInstanz #3: 250g, MHD 2026-07-10, Gefrierschrank

→ Drei VERSCHIEDENE Einheiten mit UNTERSCHIEDLICHEN MHDs!

🔄 User Workflows

Hauptworkflow: Produktinstanz hinzufügen (Einkauf)

1. Benutzer klickt "Neuen Einkauf hinzufügen"
2. Wählt Lebensmittel aus Katalog
3. Gibt ein:
   - Menge (z.B. 500)
   - Einheit (z.B. "g")
   - MHD (z.B. 2026-06-20)
   - Lagerort (z.B. "Kühlschrank")
   - Optional: Barcode, Notiz
4. Speichert
5. ProduktInstanz wird angelegt
6. Wird in Liste/Dashboard angezeigt

Workflow 2: Bestand überblicken

1. Benutzer öffnet Lager-Übersicht
2. Sieht ALLE ProduktInstanzen gruppiert:
   - Nach LebensmittelKatalog
   - Mit MHD-Status (🟢 OK, 🟡 Bald verfallen, 🔴 Verfallen)
3. Kann filtern nach:
   - Lagerort
   - MHD-Status
   - Produkt-Kategorie

Workflow 3: Verbrauch tracken

1. Benutzer hat Joghurt gegessen
2. Öffnet ProduktInstanz
3. Ändert Menge (z.B. von 500g auf 300g)
4. Oder: "Vollständig verbraucht" (Menge = 0, markiert als deleted/inactive)
5. System aktualisiert

📝 Notizen

Besonderheiten & Design-Decisions

⭐ WICHTIG: ProduktInstanz ist das Kernmodell! Eine "Packung Joghurt" = 1 ProduktInstanz mit eigenem MHD.

Dies ist NICHT wie manchmal gedacht: "LebensmittelKatalog.MHD" (global). Stattdessen: jede gekaufte Einheit trackt ihr eigenes MHD.

Beispiel: Wenn Sie 2x Joghurt kaufen mit unterschiedlichen Verfallsdaten, sind das 2 ProduktInstanzen mit jeweils eigenem MHD.

Offene Fragen

  • Sollen Barcodes eindeutig sein (Unique Constraint) oder optional?
  • Sollen MHD-Warnungen bereits beim Einkauf angezeigt werden (wenn MHD < X Tage)?
  • Ist Barcode-Scanning für MVP erforderlich oder später?

Design-Notes

ProduktInstanz sollte Transaktional atomar updatet werden (z.B. Menge + Lagerort + MHD in EINER Operation, nicht einzeln).

Performance ist kritisch: Mit 10,000+ Produktinstanzen muss die Datenbank schnell abfragen können (Indizes auf LebensmittelKatalogId, LagerortId, MHD).
