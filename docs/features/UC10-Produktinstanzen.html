UC10: Produktinstanzen mit MHD

Use-Case 10 | Status: ✅ COMPLETE (Service + WP4 UI) | Tests: 32 Service + 17 neue UI (bUnit) + 5 Unit Tests PASSING | Code: Production Ready

📋 Übersicht

Beschreibung: ZENTRALE UC! Verwaltung von konkreten gekauften Produktinstanzen mit individuellem MHD. Dies ist das Kernmodell der gesamten Anwendung.

Hauptziele

  • ProduktInstanz-Records mit eigenem MHD verwalten
  • CRUD für ProduktInstanzen
  • Jedes gekaufte Produkt = EINE ProduktInstanz (nicht ein MHD pro Lebensmittel!)
  • Lagerort, Menge, MHD tracken

Geschäftsnutzen & Design-Decision

⭐ Zentral: Eine "Portion Joghurt" = 1 ProduktInstanz mit eigenem MHD, nicht ein globales "Joghurt" MHD. Dies ermöglicht flexibles Tracking von Mehrfach-Käufen mit unterschiedlichen Verfallsdaten.

📦 Domain Model

Beteiligte Entities

Entity Rolle Beziehung
ProduktInstanz Zu verwaltende Einheit (ZENTRAL!) Primary (CRUD-Ziel)
LebensmittelKatalog Referenz-Template Foreign Key (1..1)
Lagerort Speicherort Foreign Key (0..1)

ProduktInstanz Entity

ProduktInstanz
├── Id: int (PK)
├── LebensmittelKatalogId: int (FK) ← WELCHES Produkt?
├── Menge: decimal ← WIE VIEL?
├── Einheit: string (g, ml, Stück, etc.)
├── MHD: DateTime ← WANN VERFÄLLT DIESES?
├── LagerortId: int? (FK, nullable) ← WO LAGERT ES?
├── Barcode: string (optional)
├── KaufDatum: DateTime
└── Notiz: string (optional)

BEACHTE: Kein globales "MHD pro LebensmittelKatalog"
         Jede INSTANZ hat ihr eigenes MHD!

Daten-Beispiel

LebensmittelKatalog: Joghurt (generisch)
├── ProduktInstanz #1: 500g, MHD 2026-06-20, Kühlschrank
├── ProduktInstanz #2: 500g, MHD 2026-06-25, Kühlschrank (2. gekauft)
└── ProduktInstanz #3: 250g, MHD 2026-07-10, Gefrierschrank

→ Drei VERSCHIEDENE Einheiten mit UNTERSCHIEDLICHEN MHDs!

🔄 User Workflows

Hauptworkflow: Produktinstanz hinzufügen (Einkauf)

1. Benutzer klickt "Neuen Einkauf hinzufügen"
2. Wählt Lebensmittel aus Katalog
3. Gibt ein:
   - Menge (z.B. 500)
   - Einheit (z.B. "g")
   - MHD (z.B. 2026-06-20)
   - Lagerort (z.B. "Kühlschrank")
   - Optional: Barcode, Notiz
4. Speichert
5. ProduktInstanz wird angelegt
6. Wird in Liste/Dashboard angezeigt

Workflow 2: Bestand überblicken (aktuell in UC10)

1. Benutzer öffnet /lagerbestand
2. Sieht Tabelle aller ProduktInstanzen (ungefiltert):
   - Sortiert nach Verfallsdatum (FIFO)
   - Mit Spalten: Lebensmittel-Name, Menge, Verfallsdatum, Tage bis MHD, Lagerort
3. Kann filtern nach:
   - Status: „Alle" (Standard) oder „Nur abgelaufene"
   - Lagerort: Dropdown mit vier Werten (Kühlschrank, Tiefkühler, Pantry, Anderes)
4. Verfallene Packungen werden rot hinterlegt
5. Text „Tage bis MHD" zeigt: „N Tage verbleibend", „Heute ablaufend", oder „vor N Tagen abgelaufen"

⚠️ HINWEIS: Gruppierung nach Lebensmittel, mehrfarbige Ampel (🟢🟡🔴), und Kategorie-Filter sind
Zielbilder für UC7 (Verfallsdatum-Warnungen) und nicht Teil von UC10.

Workflow 3: Verbrauch tracken

1. Benutzer hat Joghurt gegessen
2. Öffnet ProduktInstanz
3. Ändert Menge (z.B. von 500g auf 300g)
4. Oder: "Vollständig verbraucht" (Menge = 0, markiert als deleted/inactive)
5. System aktualisiert

Filter-Logik

Filter-Ablauf im UI — Drei verschiedene Zweige nach Status und Lagerort:

1. Status = „Nur abgelaufene" (ohne Lagerort):
   → GetVerfallenenAsync() (Service liefert Verfallsdatum ≤ heute)
   → UI-Nachfilter: Where(p => p.Verfallsdatum < DateTime.Today) — In-Memory, weil nur dieser Pfad in-memory nachfiltert
   → Lagerort-Nachfilter (wenn gewählt): Where(p => string.Equals(p.Lagerort, lagerortFilter, StringComparison.Ordinal))
   → OrderBy(p => p.Verfallsdatum) — Nachfilter erfordert Sortierung

2. Status = „Alle" mit Lagerort gewählt:
   → GetByLagerortAsync(lagerort) — Direkter Service-Aufruf, kein In-Memory Filter
   → OrderBy(p => p.Verfallsdatum) — Sortierung (Service gibt unsortiert zurück)

3. Status = „Alle" (ohne Lagerort, Vorgabe):
   → GetNachVerfallsdatumSortiertAsync() — bereits sortiert, keine Nachbearbeitung nötig

⚠️ WICHTIG: Die Datumsgrenze ist zwischen Service und UI unterschiedlich:
   - Service (GetVerfallenenAsync): Verfallsdatum ≤ heute
   - UI: Filtertabbelle nutzt < heute (beide Komponenten)
   - Grund: „Mindestens haltbar bis" bedeutet, dass die Packung am MHD-Tag noch gut ist.

Nutzer-Workflow: Lagerbestand filtern

  1. Benutzer öffnet /lagerbestand
  2. Standard: Alle Packungen, sortiert nach MHD (via GetNachVerfallsdatumSortiertAsync())
  3. Filter 1 — Status:
    • „Alle" (Standard): keine Änderung
    • „Nur abgelaufene": ruft GetVerfallenenAsync() auf, UI filtert < heute in-memory, sortiert danach
  4. Filter 2 — Lagerort (optional, kombinierbar mit Status):
    • Ist Status = „Nur abgelaufene": in-memory-Nachfilter (string.Equals Ordinal) auf die aus GetVerfallenenAsync
    • Ist Status = „Alle": ruft GetByLagerortAsync(lagerort) auf (direkter Service-Aufruf), sortiert danach
  5. Tabelle rendert mit: Lebensmittel-Name, Menge, Verfallsdatum, Tage bis MHD, Lagerort, Bearbeiten/Löschen-Buttons
  6. Verfallene Packungen werden mit table-danger-Klasse rot hinterlegt

Edge Cases & Leerzustände

  • Kein Lagerbestand vorhanden (Tabelle leer, keine Filter): „Kein Lagerbestand vorhanden."
  • Filter mit 0 Treffern (z.B. Status=abgelaufen+Lagerort=Kühlschrank, aber nur frische im Kühlschrank): „Keine Treffer für diesen Filter."
  • Fehlerfall beim Laden (z.B. Service Exception): Fehlerleiste oben angezeigt, Filterleiste bleibt sichtbar (Nutzer kann Filter zurücksetzen)
  • Heute ablaufende Packung (Verfallsdatum = heute):
    • Text: „Heute ablaufend" (kein red background)
    • Ist nicht im Expired-Filter enthalten (UI filtert auf <, nicht ≤)

MHD-Spalte Berechnung

NICHT im Service: Die Spalte „Tage bis MHD" wird im UI berechnet: (instanz.Verfallsdatum - DateTime.Today).Days. Pro Tabellenzeile einen Service-Aufruf wäre N+1-Abfrage.

Formatierung: Verwendet MhdTextFormatter.GetMhdText(tagesBisMhd):

  • Positive Werte: „N Tage verbleibend" (oder „1 Tag verbleibend" im Singular)
  • Null (tagesBisMhd == 0): „Heute ablaufend"
  • Negative Werte: „vor N Tagen abgelaufen" (oder „vor 1 Tag abgelaufen" im Singular)

Fehlerbehandlung

Drei unabhängige Lade-Vorgänge mit getrennten Fehlern:

  • Lebensmittel: Fehler zeigt Alert, Seite wird nicht gerendert
  • Nährwert: Fehler wird separat in der Nährwert-Sektion gezeigt, blockiert nicht die Seite
  • Packungen: Fehler wird separat in der Packungs-Sektion gezeigt, blockiert nicht die Seite

  2. Lebensmittel-Info + Nährwert werden geladen

  4. Packungen werden nach Verfallsdatum sortiert (FIFO: älteste zuerst)
  5. Tabelle rendert: Menge, Verfallsdatum, Tage bis MHD, Lagerort, „Bearbeiten"-Link
  6. Verfallene Packungen werden rot hinterlegt

Tabelle mit Spalten:
- Menge (mit Einheit aus Lebensmittel)
- Verfallsdatum (Format: dd.MM.yyyy)
- Tage bis MHD (via MhdTextFormatter)

⚠️ Wichtige Einschränkung: Lagerort-Doppelung

Der Lagerort-Filter speist sich aus LagerortKonstanten, nicht aus UC9-Lagerorte!

Das System hat zwei unverbundene Lagerort-Konzepte:

Konzept Herkunft Werte Integration
LagerortKonstanten Fest in Quellcode Kühlschrank, Tiefkühler, Pantry, Anderes ProduktInstanzService validiert dagegen
Lagerort-Entity (UC9) Freie Eingabe, Seite /lagerorte Benutzerdefiniert; alphanumerisch nur (^[A-Za-z]+$), keine Umlaute ILagerortService, wird nicht von ProduktInstanz verwendet

Folge für UC10: Der Filter zeigt nur die vier Konstanten-Werte. Ein Benutzer, der unter /lagerorte ein neues Lagerort anlegt, kann es nicht im UC10-Filter verwenden — Grund 1: es kommt nicht in das Dropdown-Menü (das aus LagerortKonstanten.AlleWerte gespeist wird). Grund 2: selbst wenn der Wert irgendwie gewählt wird, lehnt ProduktInstanzService.CreateAsync ihn ab (wird validiert). Umgekehrte Disjunktion: Die beiden Konstanten-Werte mit Umlauten (Tiefkühler, Kühlschrank) lassen sich unter /lagerorte gar nicht erst anlegen, weil UC9 nur ^[A-Za-z]+$ zulässt und Umlaute ablehnt. Damit können sich die beiden Systeme nicht einmal auf einen gemeinsamen Namen einigen. Diese Inkonsistenz ist bekannt und wird als eigenes, nicht terminiertes Vorhaben in einer Weiterentwicklung adressiert.

Case-Sensitivität: Der Lagerort-Vergleich ist in beiden Komponenten case-sensitiv (StringComparison.Ordinal in der UI-Filterung; ==-Operator im Service). Ein Datensatz mit Lagerort „kühlschrank" (Kleinbuchstaben) fällt aus einem Filter für „Kühlschrank" (Großbuchstaben) heraus.

📝 Notizen & Design Decisions

Besonderheiten & Architektur

⭐ ZENTRAL: ProduktInstanz ist das Kernmodell! Eine "Packung Joghurt" = 1 ProduktInstanz mit eigenem MHD.

Nicht global: Dies ist NICHT "LebensmittelKatalog.MHD" (ein MHD pro Lebensmitteltyp). Stattdessen trackt jede gekaufte Einheit ihr eigenes MHD.

Beispiel: Wenn Sie 2x Joghurt kaufen mit unterschiedlichen Verfallsdaten → 2 ProduktInstanzen mit jeweils eigenem MHD:

  • ProduktInstanz #1: 500g Joghurt, MHD 2026-06-20, Kühlschrank
  • ProduktInstanz #2: 500g Joghurt, MHD 2026-06-25, Kühlschrank (2. gekauft)

Performance & Indizes

Mit 10,000+ Produktinstanzen ist Performance kritisch:

  • Index auf LebensmittelKatalogId (für Filterung)
  • Index auf Lagerort (für Bestandslisten)
  • Index auf Verfallsdatum (für MHD-Warnungen)

Atomic Updates

ProduktInstanz Updates sind atomar: Menge + Lagerort + MHD in EINER Operation (nicht einzeln).

Dies verhindert Inkonsistenzen.

Zukunfts-Features (Backlog)

  • Barcode-Scanning (optional für MVP)
  • MHD-Warnungen beim Einkauf anzeigen (if MHD < X Tage)
  • Automatische Verfallsdatum-Warnung (UC7)
  • Lagerort-spezifische Einstellungen (z.B. Max Temperatur)

Abhängigkeiten

  • UC9: Lagerorte (optional)

Wird benötigt von:
