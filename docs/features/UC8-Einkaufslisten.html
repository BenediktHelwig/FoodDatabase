UC8: Einkaufslisten generieren

Use-Case 8 | Status: ✅ FERTIG (17/17 Tests GRÜN)

📋 Übersicht

Beschreibung: On-demand Generierung von Einkaufslisten basierend auf Mindestbestandsgrenzen. Wenn Gesamtmenge eines Lebensmittels den Mindestbestand erreicht oder unterschreitet (<=), wird es zur Einkaufsliste hinzugefügt.

Hauptziele

  • Flache Liste mit einem Eintrag pro Lebensmittel (aggregiert)
  • On-demand Berechnung (keine Persistierung)
  • Trigger: Gesamtmenge <= MindestbestandMenge (aggregiert über alle Instanzen)
  • Sortierung nach Lebensmittel-Name

Geschäftsnutzen

Der Benutzer sieht in Echtzeit, welche Produkte zum Einkaufen notwendig sind, ohne dass die Liste manuell gepflegt werden muss. Die Aggregation über alle Packungen ermöglicht realistische Mindestbestands-Prüfungen.

📦 Domain Model

Beteiligte Entities

Entity Rolle Beziehung
ProduktInstanz Quell-Entity für Aggregation Primary (gelesen, nicht persistiert)
LebensmittelKatalog Referenziertes Lebensmittel (Name, Einheit) Navigation Property

DTOs (On-demand, keine neuen DB-Entities)

EinkaufslistenEintragDto
├── LebensmittelKatalogId: int
├── LebensmittelName: string (mit Fallback: "Lebensmittel #ID")
├── AktuelleGesamtmenge: decimal (Sum über alle Instanzen)
├── MindestbestandMenge: decimal (aus First-Instanz)
├── Fehlmenge: decimal (Mindestbestand - Gesamtmenge)
└── Einheit: string (aus LebensmittelKatalog oder "")

Wichtige Hinweise

  • Keine neue DB-Entity: Einkaufslistendata wird nicht persistiert
  • Aggregation pro Lebensmittel: Alle ProduktInstanzen desselben LebensmittelKatalogId werden summiert
  • Trigger: `<=` nicht `<`: Wenn Menge == Mindestbestand, ist das auch Unterschreitung
  • Fallback-Handling: Wenn LebensmittelKatalog-Navigation null ist, wird "Lebensmittel #ID" verwendet

🔄 User Workflows

Hauptworkflow: Einkaufsliste generieren (On-Demand)

1. Benutzer klickt "Einkaufsliste anzeigen"
2. System ruft GetEinkaufslisteAsync() auf
3. System aggregiert ProduktInstanzen pro LebensmittelKatalogId
4. System prüft: Gesamtmenge <= Mindestbestand?
5. System generiert DTO-Liste (ein Eintrag pro Lebensmittel)
6. System sortiert alphabetisch nach LebensmittelName
7. Benutzer sieht Einkaufsliste mit Fehlmengen
8. → Keine Persistierung, kein "Abhaken"

Beispiel: Aggregation

ProduktInstanzen:
  - ID 1: Milch, Menge 500ml, Mindestbestand 1000ml
  - ID 2: Milch, Menge 200ml, Mindestbestand 1000ml

Aggregation:
  → Gesamtmenge = 500 + 200 = 700ml
  → Mindestbestand = 1000ml
  → 700 <= 1000? JA → In Einkaufsliste
  → Fehlmenge = 1000 - 700 = 300ml

📝 Besonderheiten & Bekannte Einschränkungen

Design-Entscheidungen

  • On-Demand, nicht persistiert: Einkaufsliste wird bei jedem Aufruf neu berechnet (keine DB-Performance-Überlegung, aber auch keine Konsistenz-Probleme)
  • Flache Liste, ein Eintrag pro Lebensmittel: Mehrere ProduktInstanzen desselben Lebensmittels werden aggregiert → Übersicht
  • Trigger `<=` nicht `<`: Wenn Menge exakt Mindestbestand erreicht, ist es bereits ein Unterschreitung (nicht erst darunter)
  • Keine Abhaken-Logik: UC8 ist rein read-only. Gekaufte Waren werden später durch UC6 (VerbrauchAusbuchung) verwaltet

Bekannte Einschränkung

Lebensmittel ohne Instanzen: Wenn ein Lebensmittel keine ProduktInstanzen hat (komplett verbraucht), kann es nicht auf der Einkaufsliste erscheinen, da Mindestbestand auf Instanzen lebt. Das ist eine akzeptierte Lücke der aktuellen Architektur.

🔄 Phase-2 Vorgriff

Der Service ist designet für Erweiterung:

  • BackgroundService kann später `GetEinkaufslisteAsync()` periodisch aufrufen
  • Push-Benachrichtigungen könnten an diese Liste andocken
  • Mobile App könnte Read-Only Zugriff bekommen

Keine Änderungen nötig; der Service ist bereits extensible.
