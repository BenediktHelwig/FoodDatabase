UC7: Verfallsdatum-Warnungen

Use-Case 7 | Status: ✅ FERTIG (19/19 Tests GRÜN)

📋 Übersicht

Anforderung: Automatische Überwachung von Verfallsdaten mit Warnstufen-Anzeige. On-demand berechnet beim Öffnen der Warnliste — keine Persistierung, keine Benachrichtigungen (Phase 2+).

Warnstufen

  • 🟢 Ok: Verfallsdatum > 3 Tage entfernt
  • 🟡 BaldAblaufend: Verfallsdatum in 0–3 Tagen (MHD == heute ⇒ Gelb!)
  • 🔴 Abgelaufen: Verfallsdatum überschritten (negative Tage)

Besonderheiten

  • Sortierung: Abgelaufene zuerst, dann nach Datum aufsteigend
  • Integration mit UC6: Verbrauchte Produkte verschwinden automatisch aus der Warnliste
  • Berechnung: `(ProduktInstanz.Verfallsdatum - Heute).Days` → rein on-demand, keine DB-Änderung

Beteiligte Entities

Entity Felder Rolle
ProduktInstanz Id, Verfallsdatum, Menge, LebensmittelKatalogId Quelle (existiert bereits)

Neue Enum + DTOs

public enum VerfallsdatumStatus
{
    Ok = 0,
    BaldAblaufend = 1,
    Abgelaufen = 2
}

public class VerfallsdatumWarnungDto
{
    public int ProduktInstanzId { get; set; }
    public string LebensmittelName { get; set; }
    public DateTime Verfallsdatum { get; set; }
    public int TageBisAblauf { get; set; }  // negativ = abgelaufen
    public VerfallsdatumStatus Status { get; set; }
}

⚠️ Keine persistierte Entity

Umgehung: Warnstufen werden on-demand berechnet aus ProduktInstanz.Verfallsdatum. Kein VerfallsdatumWarnung-Entity, keine EF-Migration, keine Synchronisationsprobleme.

Warum TimeProvider?

🔄 User Workflows

Workflow: Warnliste anzeigen

1. Benutzer öffnet "Warnungen"-Seite
2. System ruft GetWarnungenAsync() auf (~millisekunden)
3. Berechnung: Verfallsdatum - Heute für alle Produkte
4. Filterung: nur BaldAblaufend + Abgelaufen
5. Sortierung: Abgelaufene zuerst
6. Anzeige: Liste mit Warnstufen-Farben
7. Benutzer sieht sofort: "2 Produkte bald verfallen, 1 abgelaufen"

Integration mit UC6

Wenn UC6 eine ProduktInstanz löscht oder konsumiert → nächster Aufruf von GetWarnungenAsync() gibt die verbrauchte Instanz nicht mehr zurück (Repository-Abfrage liefert sie nicht). Keine Synchronisations-Logik nötig.

📝 Implementierungs-Notizen

On-Demand-Strategie (Phase 1)

Warnungen werden zur Laufzeit berechnet, nicht gespeichert. Grund: Verfallsdatum ist eine unveränderliche Basis-Information; die Warnstufe ergibt sich jederzeit automatisch aus der Tagesberechnung. Keine Persistierung = keine Sync-Fehler.

Phase 2+ Vorgriff: Push-Benachrichtigungen

Die `TimeProvider`-Injektion und saubere Service-Schnittstelle ermöglichen später einen BackgroundService, der z.B. stündlich prüft und Benachrichtigungen versendet — ohne UC7 zu ändern. Die `BerechneStatus()`-Funktion bleibt das zentrale Rechenwerk.
